## Problem

个人名下几十个仓库的合并设置、Issue / PR 模板、标签和提交信息风格各不相同. 存量仓库已有两种提交风格 (`type(scope): 描述` 和 `[type]: 描述`) 和大量无格式提交, 一刀切会让历史全部报错; 私有仓库在免费计划下又不能用规则集硬性阻止

## Decision

新建独立子项目 `governance`, 沿用仓库卫生的流程: 每周和手动只读扫描, 写一张按仓库勾选的审阅单, 由 `HengXin666` 加 `apply` 标签或手动运行执行. 执行时重新读取仓库再决定, 合并设置和标签直接调用接口, 标签只建、改、改名不删除. 写入目标仓库的文件统一放在一个 `governance/setup` PR 里, 不直接推默认分支

提交风格按 覆盖配置, 已接入文件, 审阅单, 最近 200 个提交的主导风格, 默认约定式 的顺序决定. 接入时记录默认分支最新提交为基线, 基线及之前的提交不检查. 目标仓库得到一份只用标准库的 `commit_lint.py`, CI 和本地 commit-msg 钩子共用; PR 标题不合规时检查失败并评论建议标题, squash 使用 PR 标题, 因此合规标题即合规提交. 推送到默认分支只能事后报告

规则集只给公开仓库, 且等 commit-lint 工作流已经在默认分支上再创建, 绕过名单为空但不要求审批. 检测到工作流会直接推默认分支时默认不建. 私有仓库只靠检查失败和钩子提醒

## Alternatives considered

- 什么都不做 / 复用现有: 各仓库手工配置零开发量, 但几十个仓库难以保持一致, 也无法对存量历史设基线. 直接扩展 hygiene 能复用其审阅单流程, 但 hygiene 的职责是清理分支和 Skill, 且有进行中的本地改动, 混在一起会让两套勾选和执行互相牵连, 因此只借鉴其结构, 代码独立
- 直接推送默认分支写文件: 最快生效, 但绕过了用户自己的审阅, 也会被已有保护规则拦住, 用户决定改为每仓库一个 PR
- 用 commitlint / husky 等 npm 工具: 生态成熟, 但要给每个仓库引入 Node 依赖, 非 JS 仓库负担重, 因此用一个标准库 Python 脚本
- 对全部提交强制统一一种风格: 规则最简单, 但存量仓库的历史会全部报错, 也违背已有的书写习惯, 因此沿用主导风格并设基线
- 立即为所有仓库建规则集: 能最早拦截, 但在检查还不存在时要求它会锁死默认分支, 私有仓库在免费计划下也无法使用, 因此只对公开仓库并延后到检查落地

## Consequences

审阅单会列出私有仓库名字, 但不含其代码. 公开仓库需要先合并治理 PR 再执行一次才有规则集; 有推送类工作流的仓库要在配置里显式允许. `HYGIENE_TOKEN` 需要额外的 `workflow` 权限才能写入 commit-lint 工作流. 目标仓库里的 `commit_lint.py` 是本目录同名文件的副本, 修改后需要再执行一次治理同步
